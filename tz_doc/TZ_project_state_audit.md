## 2. Создание структуры `00_PROJECT_STATE`

Создать папку `00_PROJECT_STATE/` в корне проекта со следующей структурой и файлами.  
Все `.md`-файлы создаются **пустыми шаблонами** — наполнение будет выполнено на этапе 4 (аудит).

```
00_PROJECT_STATE/
├── memory/
│   ├── failures.md
│   └── lessons.md
├── active_tasks.md
├── current_state.md
├── decisions_log.md
├── HANDOFF_SNAPSHOT.md
├── known_problems.md
├── lessons.md
├── next_steps.md
├── WALKTHROUGH_TEMPLATE.md
└── walkthrough.md
```

### Назначение каждого файла

| Файл | Назначение |
|------|------------|
| `memory/failures.md` | Хронологический лог провалов, ошибок и тупиков. Каждая запись: дата, описание, причина, что изменено. |
| `memory/lessons.md` | Извлечённые уроки из `failures.md`. Формат: принцип + обоснование. |
| `active_tasks.md` | Список задач в статусе `IN PROGRESS` на текущий момент с приоритетом и блокирующими зависимостями. |
| `current_state.md` | Снэпшот текущего состояния проекта: что работает, что сломано, какой последний успешный релиз. |
| `decisions_log.md` | Архив архитектурных решений: что выбрано, почему, какие альтернативы отклонены. |
| `HANDOFF_SNAPSHOT.md` | Документ передачи контекста новому агенту или сессии. Самодостаточное описание проекта за 5 минут чтения. |
| `known_problems.md` | Известные баги и ограничения с пометкой: `[OPEN]`, `[MITIGATED]`, `[CLOSED]`. |
| `lessons.md` | Корневой файл уроков (верхний уровень) — синтез из `memory/lessons.md` + архитектурные выводы. |
| `next_steps.md` | Приоритизированный бэклог следующих шагов. Формат: приоритет / задача / блокирует что. |
| `WALKTHROUGH_TEMPLATE.md` | Стандартный шаблон для walkthrough-отчётов агента. |
| `walkthrough.md` | Последний актуальный walkthrough текущего спринта. |

## 3. Шаблоны файлов

При создании заполнить каждый файл минимальной структурой (не содержимым — это этап 4):

```markdown
# Walkthrough: [Название задачи] ([Версия ТЗ])

## Статус
<!-- COMPLETED / IN PROGRESS / FAILED -->

## Изменения
<!-- Что было сделано -->

## Верификация
<!-- Результаты тестов, логи, таблицы -->

## Открытые вопросы
<!-- [НЕТ ДАННЫХ] или известные проблемы после выполнения -->
```

### `HANDOFF_SNAPSHOT.md`
```markdown
# HANDOFF SNAPSHOT — [Дата]

## Что это за проект
<!-- 2-3 предложения -->

## Текущее состояние (одна строка)
<!-- Пример: "Пайплайн работает, StarVector 8B активен, следующий спринт — photos/" -->

## Структура проекта
<!-- Краткое дерево ключевых папок -->

## Как запустить пайплайн
<!-- 3 команды -->

## Что сейчас сломано / ограничено
<!-- Ссылка на known_problems.md -->

## Следующие шаги
<!-- Ссылка на next_steps.md -->
```

### Остальные `.md`-файлы
Создать с заголовком H1 и пустой секцией:
```markdown
# [Название файла]

<!-- Заполняется в ходе аудита (Этап 4) -->
```

## 4. Анализ и аудит проекта

После создания структуры — провести полный аудит `c:\svg_builder`.  
Метод: читать файлы, скрипты, логи, git-историю. Не генерировать — фиксировать факты.

### 4.1 Анализ кодовой базы

Прочитать и проанализировать:
- `ops/scripts/*.py` — все скрипты пайплайна
- `00_governance/ontology_v1.json`, `design-tokens.json`, `passport_schema_v1.json`, `AGENTS.md`
- `03_knowledge_graph/*.json` — граф знаний
- `04_passports/*.md` — паспорта объектов
- `ops/logs/*.jsonl` — все доступные логи

### 4.2 Анализ git-истории

```bash
git log --oneline --all | head -30
git diff HEAD~5 HEAD --stat
```

Зафиксировать: что менялось, в каком порядке, были ли откаты.

### 4.3 Анализ текущего состояния пайплайна

```bash
# Проверить работоспособность каждого скрипта
```

## 5. Заполнение файлов `00_PROJECT_STATE`

На основе проведённого анализа заполнить каждый файл реальными данными:

### `current_state.md` — заполнить по структуре:
- Версия спецификации: `TZ_v2.9`
- Последний успешный релиз: ветка `master`, дата коммита
- Активный движок: StarVector 8B INT4, Windows-native
- VRAM при инференсе: ~5.1 ГБ
- Количество обработанных объектов: 5 (COMP-001–005)
- Статус QA: 0 failures
- Что сломано / ограничено: из `known_problems.md`

### `known_problems.md` — заполнить из реальных данных:
Включить минимально:
- `[CLOSED]` — пустые SVG (раздел 24 ТЗ)
- `[CLOSED]` — viewBox-мисматч (раздел 27–28 ТЗ)
- `[CLOSED]` — CPU-only torch (раздел 25 ТЗ)
- `[OPEN]` — StarVector fallback на Windows при отсутствии fairscale (R-01)
- `[OPEN]` — агрессивная цветовая фильтрация при малом числе foreground-paths (R-03)
- Любые новые проблемы, выявленные в ходе аудита

### `decisions_log.md` — перенести ключевые решения из ТЗ:
- Foundation-First парадигма
- Промежуточный паспорт объекта как декларативный слой
- Выбор VTracer + StarVector (не облако)
- Zero Black Policy
- Стратегия цветовой фильтрации через RGB-расстояние
- Windows-native INT4 вместо WSL2

### `memory/failures.md` — хронология провалов:
- Пустые SVG при первом запуске на реальных PNG
- CPU-only torch при попытке INT4
- viewBox-мисматч COMP-001
- Любые другие из git-лога и `ops/logs/`

### `memory/lessons.md` — извлечь принципы:
- Тестировать пайплайн на реальных данных, не заглушках
- PIL-санитизация PNG до VTracer обязательна
- `xml.etree.ElementTree` валидация должна быть на этапе инференса, не только QA
- Прочие из анализа

### `next_steps.md` — приоритизированный бэклог:
```markdown
## Приоритет HIGH
- [ ] Спринт `input/photos/`: дедупликация, переименование, UI-crop (см. TZ_photos_pipeline.md)

## Приоритет MEDIUM
- [ ] Задача cat_3 / классификация животных (отложена)
- [ ] ND-04: определить формат SVG-вывода (inline / standalone / sprite)
- [ ] ND-06: политика версионирования паспортов при повторной деконструкции

## Приоритет LOW
- [ ] ND-01: проверить find-skills и scope-пути скилов
- [ ] ND-08: зафиксировать путь HF-кэша в конфигурации
```

### `HANDOFF_SNAPSHOT.md` — заполнить полностью:
Документ должен быть самодостаточным. Новый агент, прочитав его за 5 минут, должен понять: что это, как запустить, что не трогать, что делать дальше.

### `lessons.md` (корневой) — синтез:
Архитектурные принципы, выведенные из всего пути проекта. Не хронология — выжимка.

### `walkthrough.md`:
Скопировать последний актуальный walkthrough (StarVector 8B + viewBox-нормализация).
