## 0. Контекст
Пользователь выгрузил папку `input/photos/` (≈171 файл). Проблемы:
1. **Дубликаты разного веса** — каждое фото `photo_N` продублировано миниатюрой
   `photo_N_thumb` (легче). Нужны только полноразмерные оригиналы.
2. **Грязный кадр** — многие файлы это скриншоты ленты Instagram: вокруг рисунка
   статус-бар телефона, шапка поста, панель лайков/комментариев, нижняя навигация.
   Для распознавания и рендера нужен только сам рисунок.

## 1. Дедупликация (`удалить дубликаты, которые весят меньше`)
- Группировка по перцептивному хэшу (dHash 8×8, Хэмминг ≤ 6) — ловит и пары
  full/thumb, и кросс-дубликаты под разными номерами.
- В каждой группе остаётся **самый тяжёлый** файл (наибольший размер в байтах =
  наилучшее качество), остальные удаляются.
- Каждое удаление логируется (что оставлено, что удалено, размеры).

## 2. Переименование (по README `input/`)
- Шаблон README: `[описание]_[id].[ext]`, без пробелов/кириллицы/спецсимволов.
- Имя: `photo_` + `f"{i:03d}"` → `photo_001.jpg`, `photo_002.jpg`, …
- Порядок `i` — натуральный по исходному номеру (photo_1, photo_2, … photo_86),
  после дедупа сквозная перенумерация 001..K.

## 3. Авто-обрезка UI (новый агент A00 «de-chrome», `ops/scripts/autocrop.py`)
Определяет, где начинается рисунок и где меню телефона/приложения, и обрезает лишнее.

**Метод (детерминированный, локальный, без сети):**
- Рисунок = крупная светлая область (белый/светлый фон) с органическим контентом;
  UI = тёмные сплошные полосы (тёмная тема) либо плотные полосы текста/иконок.
- Итеративное профилирование яркости: доля «светлых» пикселей по строкам и
  столбцам; наибольший непрерывный «светлый» прогон (с мостами через мелкие
  разрывы) = границы рисунка. 3 итерации строки↔столбцы для уточнения bbox.
- Покрывает два режима: (A) светлый прямоугольник рисунка в тёмном UI →
  найти прямоугольник; (B) рисунок на весь кадр + тонкая тёмная полоса
  навигации → срезать полосу.

**Предохранители (против разрушения картинки):**
- bbox ≥ 30% ширины и высоты исходника; разумное соотношение сторон (0.2–5.0);
  длинная сторона ≥ 256 px (минимум README). Иначе — обрезка отменяется.
- Низкая уверенность (нечёткая граница UI↔рисунок) → обрезка не применяется,
  файл помечается в отчёте на ручную проверку.
- Если bbox ≈ весь кадр (срез < 8%) → файл уже чистый, обрезка не нужна.

## 4. Резервная копия перед обрезкой (`на случай ложного срабатывания`)
- Перед обрезкой оригинал копируется в `input/photos/_precrop_originals/`.
- Копируются **только** файлы, которые реально обрезаются. Папка `_precrop_*`
  исключается из дальнейшего сканирования пайплайном.
- Откат любого файла = вернуть копию из `_precrop_originals/`.

## 5. Интеграция в пайплайн
Порядок: **A00 autocrop → A01 deconstruct → A02 validate → A05/A08 compile**.
- `deconstruct.py` сканирует `input/` **рекурсивно** (включая `input/photos/`),
  пропуская каталоги, начинающиеся с `_` (резервные/служебные).
- README `input/` дополняется шагом 0 (авто-обрезка).
- Обрезанная картинка попадает в `01_input_raster/...` штатным копированием A01,
  поэтому рендер использует уже очищенный кадр.

## 6. Прогон и отчёт
После дедупа+переименования+обрезки и проверки кадров — полный прогон
`deconstruct → validate → compile`. Отчёт: сколько удалено дублей, сколько
обрезано/уже чистых/на ручную проверку, как распознаны (классы/режимы),
сколько отрендерено vs карантин.
